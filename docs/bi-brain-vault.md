# Portable Bi Brain vault, schema 1

The runtime vault for `data/brain.sqlite` is `data/brain.vault/` by default. Each database filename gets its own vault so test and restore databases cannot share generations. Its `manifest.json` points to exactly one complete generation under `generations/<UUID>/`. Open the named `state.json` for machine-exact project, source, source-version, entity, and entity-version records. Open the sibling `raw/*.txt` for UTF-8 original source versions and `wiki/`, `intent/`, `claims/`, `dreams/`, `handoff/`, `links/` Markdown for readable content. Each readable file has a sibling JSON record with stable ID, project, version, data, timestamps and evidence references. IDs are UUIDs or constrained existing IDs; file names are built from validated IDs, never user titles. `source_id` and `source_version` are stable provenance references. A source version's SHA-256 content hash is in its raw metadata. Later corrections create new version files.

`manifest.json` declares `schema_version`, generation UUID, state path and SHA-256 hash. Read only its generation. A reader detects edits by verifying the hash; external changes are not authority. Git is initialized inside the runtime vault, with no remote. It is independent of the application-code repository. `data/brain.vault-protected/` is outside that Git root and holds original raw copies, `raw/quarantine/`, the pending journal, and a consistent pre-migration SQLite backup. Both directories are local private data and must not be published. Scanner `bounded-secrets-v1` recognizes private-key headers, representative API token patterns and assigned long secrets; it cannot detect arbitrary credentials. A detected raw original remains only in protected quarantine; the query projection and portable generation contain an explicit redacted placeholder. The owner sees a warning. Treat a vault as sensitive even after scanning.

Every publication stages a complete generation in a protected journal, records its generation in the SQLite transaction, then atomically replaces the manifest and makes a local Git commit. After the manifest changes, superseded generation directories leave the working tree; their history remains in managed Git until a permanent forget sanitizes it. On startup, only a journal whose generation matches the committed SQLite marker is replayed; an uncommitted stage is discarded. A failed Git commit does not remove the journal and requires recovery. Acknowledged captures are durable in SQLite and a published portable generation. The published manifest is the restart authority: startup rebuilds a divergent SQLite knowledge projection from it. Runtime services use SQLite as a short-lived transactional working set and query store. Direct external Markdown edits are not accepted; altered machine state fails hash validation. The service-read migration to manifest-backed views is still incomplete.

Existing SQLite installations should run `npm run vault:dry-run` after stopping the app. `npm run vault:migrate` creates the consistent `pre-vault.sqlite` backup, migrates stable IDs and publishes a generation. `npm run vault:rebuild` reconstructs the SQLite knowledge projection and FTS from the current manifest while retaining operational jobs/grants. `npm run vault:rollback` creates a verified separate database copy from the pre-migration backup; it never overwrites the current database. Stop the app and select that copy deliberately. The production startup also creates the vault if absent; take a separate operational backup first for a production upgrade.

Permanent deletion removes source versions from SQLite and managed generation history, then creates a sanitized local Git root. This sacrifices old generation revertability. A tombstone without source text remains in the current generation. Protected raw and quarantine copies for that source are deleted. A protected `sanitize.pending` marker makes interrupted managed-history sanitation resumable at startup or with `vault:finalize-forget`; the new complete generation is published before older generations are removed. The managed pre-migration backup is replaced with a sanitized SQLite snapshot. The deletion response includes a persisted operation ID and read-after-delete results for managed files, history, search, derived records, and the managed backup. Embeddings and graph storage are reported as unconfigured if their tables are absent. Unmanaged copies and earlier client/provider deliveries cannot be recalled. Full external-copy proof remains an S6 gate.

The worker writes readable daily `dreams/YYYY-MM-DD.md` receipt aggregations inside each published generation. Entries are keyed by run or receipt ID and retain outcome, input hash, provider/policy, cost status, result and evidence references. These files record observed worker outcomes; they are not evidence of a live model call unless the individual receipt says so. Managed Git remains local. The owner can revert the latest accepted plan commit through the guarded API: it checks the exact HEAD, goal version and deletion tombstones, uses `git revert`, rebuilds the projection and adds an audit receipt. Later work is never overwritten; non-head reverts require manual comparison. The regular UI's Undo is a version-checked compensating revision.
