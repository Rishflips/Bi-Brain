## Why the current app cannot just be uploaded

The installed Sites skills specify Cloudflare Worker-compatible server output, D1 structured persistence, R2 blob storage, dispatch-owned ChatGPT identity, and HTTP MCP. The current local app uses Node SQLite, filesystem generations/Git subprocesses, a Fastify listener, and a permanently polling Node worker. Its MCP adapter is stdio and accepts only a loopback API URL.

Deploying only `dist/web` would leave the user interface without its working brain. A Sites version requires runtime adapters, tested authorization and durable background execution.

| React/Vite interface | Reuse product components/styles in a Sites-compatible build; retain all real flows |
| Fastify listening process | Worker fetch/API routes with shared validation and domain policy |
| node:sqlite synchronous storage | Async D1 repository and generated migrations; preserve atomic domain invariants |

## Two runtime decisions to settle before a large port

### A. Git-backed vault semantics

Sites' documented Worker deployment is not a persistent local Git host. Recommended Sites-native design: immutable revision records, compensating revert, portable vault export and local Git support in the retained local edition. This preserves useful reversible history but changes the earlier literal runtime `git revert` requirement. Record the decision and obtain owner agreement before changing that product contract.

If literal server-side Git revert is mandatory, use a hybrid: Sites provides the application surface and an authenticated HTTPS Node service hosts SQLite/Git/the worker on persistent disk. The user still sees one suite, but this requires a separately operated backend. Never connect a deployed Site to localhost or imply the laptop is an always-on backend.

### B. Jobs while the Site is closed

Sites documentation supports recurring cloud updates through authenticated writers. The current callable tool inventory did not expose a Sites create_schedule tool; do not assume an unattended scheduler is immediately available. Re-discover supported scheduling and worker capabilities during implementation. Do not assume arbitrary Cloudflare Cron, Queues or Durable Object bindings are available through Sites merely because the runtime is Cloudflare.

Run a small capability proof first: a supported unattended caller invokes a bounded, authorized job tick and a fresh read confirms a receipt after the browser is closed. Lease recovery, fencing, idempotency, source revalidation, budget reservation and activity cancellation must survive the port. If provider latency exceeds allowed execution duration, use a supported durable execution mechanism; waitUntil/browser polling is not a substitute for durable scheduling.

If the necessary dispatcher is unavailable, report that exact gate and offer the authenticated hybrid backend. A private manual-use preview may still ship, but cannot be called always-on proactive production.

Retain a local adapter and test the same contract against both. Use generated, inspected, append-only schema migrations; no runtime CREATE/ALTER schema initialization. Verify D1 search support and query behavior rather than assuming local FTS tables transfer unchanged.

Use the trusted Sites identity only through its documented dispatch boundary. For a private single-owner release, explicitly restrict owner operations to that owner. A signed-in visitor must not automatically become the owner. Service credentials reach the Site but do not manufacture a user identity, owner rights or connector consent. Keep narrow job and agent scopes, CSRF/origin checks, safe errors and rate limits suited to the actual host.
